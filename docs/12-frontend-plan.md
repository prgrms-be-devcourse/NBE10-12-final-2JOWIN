## 2. 부하 점검 — 오너가 전 화면을 만들 수는 없다

먼저 산수를 맞춰야 계획이 계획이 된다. **E의 4주는 약 20일**이고, `11-work-breakdown.md` §6이 이미 인프라로 대부분을 채워 두었다.

| E의 기존 인프라 작업 | 추정 |
| --- | --- |
| Flyway V1 베이스라인 (25테이블·제약·인덱스) | 2일 |
| 공통 스켈레톤 · ErrorCode enum · 채번 로직 | 1일 |
| CI 3잡 (build · flyway-validate · version-check) | 2일 |
| AWS 배포 파이프라인 | 3일 |
| 모니터링 스택 (Prometheus·Loki·Grafana) | 2일 |
| 성능 측정 · 장애 시연 | 2일 |
| **소계** | **12일** |

남는 것은 **8일**이다. 여기에 프론트 공통 기반 3일을 빼면 **5일**이 남고, 화면은 **23개**(구성원 앱 14 · 관리자 4 · 고객 5)다. 화면당 2시간이 채 안 된다 — 견적 편집기 하나도 그 안에 들어가지 않는다.

> 셈 기준: 23은 **페이지 단위**(04-user-scenarios.md §7과 동일). §3 배분 표의 합계 33은 **모달·보조 화면을 개별 항목으로 센 것** — 같은 대상을 배분용으로 더 잘게 나눈 수치다.

### 그래서 이렇게 나눈다

> **E는 프론트엔드의 "플랫폼"을 소유하고, 각 도메인 화면은 그 도메인의 백엔드 담당자가 만든다.**

| 구분 | 담당 | 내용 |
| --- | --- | --- |
| **프론트 플랫폼** | **E** | 프로젝트 골격 · 라우팅 · API 클라이언트 · 인증 처리 · 에러 처리 · 테마 · MSW · 공통 컴포넌트 · **코드 리뷰와 통합** |
| **소유자 없는 화면** | **E** | 로그인 · 고객 열람 페이지 5종 (제품의 얼굴이라 오너가 직접 마감) |
| **도메인 화면** | A · B · C · D | 자기 백엔드 도메인의 화면 |

**도메인 담당자가 자기 화면을 만들면 계약 불일치가 그 자리에서 드러난다.** DTO에 필드가 빠졌거나 에러 코드가 안 맞으면, 화면을 붙이는 순간 본인이 발견한다. 이건 부하 분산이자 품질 장치다.

## 4. 커트라인 — 밀리면 여기까지만

3주 금요일 게이트는 "발송 → 열람 → 승인 → 주문 전환 E2E 관통"이다. **그 한 줄기를 사람에게 보여주는 데 필요한 화면은 10개뿐이다.**

| # | 화면 | 담당 |
| --- | --- | --- |
| 1 | 로그인 | E |
| 2 | 대시보드 | D |
| 3 | 고객사 목록 · 등록 | B |
| 4 | 딜 보드 | C |
| 5 | 딜 상세 | C |
| 6 | 견적 편집기 | C |
| 7 | 발송 모달 | C |
| 8 | **고객 열람 페이지** | E |
| 9 | **승인 확인 모달** | E |
| 10 | 주문 상세 (딜 상세의 주문 탭으로 대체 가능) | C |

**나머지 13개는 여유가 생기면 만든다.** 상품 등록·구성원 초대는 **시드 데이터로 대체**해도 시연이 성립한다(이미 등록된 상태로 시작). 감사 로그·관리자 페이지·알림 설정은 없어도 서사가 끊기지 않는다.

> 2주 금요일에 이 10개 중 5개 미만이면 그때 나머지를 공식적으로 버린다. **미리 정해두는 것이 이 절의 목적이다.**

## 5. 목 우선 개발 (MSW)

### 5.1 왜 되는가

**DTO 설계서가 완성돼 있다.** 요청·응답 record가 전부 확정이라 가짜 응답을 만드는 데 추측이 필요 없다. 백엔드가 한 줄도 없어도 화면을 끝까지 만들 수 있다.

```
08-dto.md DTO ──→ shared/api/types.ts ──┬──→ 화면 (TanStack Query)
                                       └──→ mocks/handlers (MSW)
```

**타입을 한 곳에서만 정의하고 목과 화면이 같은 타입을 쓴다** — 목만 맞고 실제는 틀리는 사고를 타입이 막는다.

### 5.2 픽스처는 시연 데이터와 같은 것을 쓴다

`04-user-scenarios.md` 시나리오의 인물과 회사를 그대로 쓴다.

| 대상 | 값 |
| --- | --- |
| 회사 | 한빛오피스 (구성원 6명) |
| 구성원 | 김서연(기업 관리자) · 박지훈(영업) · 최민아(영업) |
| 고객사 | 도담건설(이수정 대리) · 성원산업 · 대한물산 · 신영건설 |
| 상품 | 1200 사무책상 · 메쉬 의자 · 수납장 등 8종 |
| 딜 | 각 단계에 2~5건, 성사 3건 |
| 견적 | 발송·열람·승인·반려 상태 각 1건 이상 |

**이 한 세트가 목 데이터이자 백엔드 시드이자 시연 데이터다.** E가 `mocks/fixtures.ts`와 Flyway seed를 같은 내용으로 만든다. 시연 때 새 데이터를 만들 필요가 없고, 개발 중 보던 화면이 그대로 시연 화면이 된다.

### 5.3 실 API로 갈아타는 시점

| 시점 | 상태 |
| --- | --- |
| 1주차 | 전부 목. 백엔드는 아직 골격 |
| **2주 금 게이트** | **인증만 실 API**(A의 로그인·refresh 완료) · 나머지 목 |
| 3주차 | 도메인별로 완성되는 대로 하나씩 전환 (`.env` 플래그로 도메인 단위 on/off) |
| **3주 금 게이트** | **전면 실 API** — E2E 관통 |

전환은 `VITE_MOCK_DOMAINS=quote,order` 같은 환경변수로 도메인 단위로 끈다. **한 번에 다 갈아타지 않는다.**

## 6. 공통 기반 — E가 1주차에 만든다

### 6.1 프로젝트 구조

```
src/
  app/              라우터 · 프로바이더 · Theme 설정
  shared/
    api/            client.ts · errors.ts · types.ts (DTO 미러)
    ui/             EmptyState · ErrorCallout · PageHeader · StatusBadge · Money
    lib/            날짜·금액 포맷
  domains/
    auth/ member/ customer/ product/ deal/ quote/ order/ activity/ notification/ dashboard/
      api.ts  hooks.ts  components/  pages/
  mocks/            handlers/ (도메인별) · fixtures.ts
```

**도메인 폴더가 `11-work-breakdown.md`의 백엔드 도메인과 1:1이다.** 소유 경계가 프론트에 그대로 옮겨지므로, "누가 이 파일을 고치는가"가 백엔드와 같은 규칙으로 정해진다.

### 6.2 라우팅 3분리

| 경로 | 대상 | 레이아웃 |
| --- | --- | --- |
| `/` | 구성원 앱 | 좌측 사이드바(접힘 가능) + 인증 가드 (`10-screen-design.md` §3.1) |
| `/admin` | 플랫폼 관리자 | 별도 인증 가드 · 단순 레이아웃 |
| `/q/:token` · `/invite/:token` · `/password-reset` | 비로그인 | **레이아웃 없음** — 앱 UI를 상속하지 않는다 (`10-screen-design.md` §1) |

### 6.3 API 클라이언트에서 반드시 처리할 것

| # | 항목 | 내용 |
| --- | --- | --- |
| 1 | **access 만료 시 재발급 큐잉** | 동시에 여러 요청이 401을 받으면 **refresh는 한 번만 호출**하고 나머지는 대기시켰다가 새 토큰으로 재시도. 이걸 안 하면 회전된 토큰이 동시에 쓰여 **`REUSE_DETECTED`로 세션 전체가 폐기된다**(전이표 §9) |
| 2 | 재발급 실패 | `REFRESH_TOKEN_NOT_ACTIVE`(401) → 즉시 로그인 화면 + "세션이 만료되었습니다" (AU-12) |
| 3 | 에러 문구 매핑 | `ErrorCode` → 문구는 **API 명세서 부록 표를 그대로** 상수화. 프론트에서 새로 쓰지 않는다 |
| 4 | `STALE_VERSION` | 409 수신 시 해당 쿼리 무효화 + "새로고침 후 다시 시도" 안내 |
| 5 | 404 통일 | 존재/권한을 구별해 말하지 않는다 (SC-09) |
| 6 | **refresh = 쿠키 (확정)** | 인증 요청에 **`credentials: 'include'`**를 붙인다. **프론트는 refresh 값을 읽지도 저장하지도 않는다** — `HttpOnly`라 JS에서 접근 자체가 불가능하고, 그게 목적이다. `localStorage`에 토큰을 넣는 코드가 들어오면 리뷰에서 막는다 |
| 7 | access token 보관 | **메모리에만**(모듈 변수 또는 Query 캐시). 새로고침 시 사라지므로 앱 부팅 시 `/auth/refresh`를 한 번 호출해 복구한다 — 쿠키가 살아 있으면 로그인 상태가 이어진다 |
| 8 | 로그아웃 | 서버가 쿠키를 지우므로(`Max-Age=0`) 프론트는 **메모리의 access만 버리고 캐시를 비운다** |

### 6.4 TanStack Query 규약

| 항목 | 규칙 |
| --- | --- |
| queryKey | `[도메인, 리소스, 파라미터]` — 예: `['quote','detail',quoteId]` · `['deal','list',filters]` |
| 낙관적 락 | mutation 응답의 `version`을 캐시에 반영. `STALE_VERSION`이면 invalidate 후 재조회 유도 |
| 폴링 | **알림만** `refetchInterval: 30_000` · `refetchIntervalInBackground: false` (탭 비활성 시 중단) |
| 목록 | 공통 `PageResponse<T>` — `page=0&size=20`, 최대 100 (Q-39) |

### 6.5 공통 컴포넌트 (Radix Themes 위에 얹는 것)

| 컴포넌트 | 역할 |
| --- | --- |
| `StatusBadge` | 딜 단계·견적 상태·열람 여부를 `10-screen-design.md` §6.1 색 규칙대로 |
| `Money` | 원 단위 정수를 3자리 구분해 표시 |
| `EmptyState` | 빈 목록에서 다음 행동 제안 (`10-screen-design.md` §6.2) |
| `ErrorCallout` | ErrorCode를 받아 부록 문구로 렌더 |
| `PageHeader` | 제목 · 배지 · 액션 버튼 자리 |
| `ConfirmDialog` | `AlertDialog` 래퍼 — 되돌릴 수 없는 행동 3종이 같은 모양이 되도록 |

| 시점 | 기존 조건 | **추가할 프론트 조건** |

| **E가 병목** | 3주차에 배포·모니터링과 프론트 통합이 겹친다 | 3주차 E의 프론트 몫을 **통합·리뷰로만** 한정. 새 화면을 3주차에 배정하지 않는다 |
| **목과 실 API 불일치** | 목이 DTO를 느슨하게 흉내내면 전환 때 터진다 | 타입을 한 곳에서만 정의 · 도메인 단위 점진 전환 · 2주 금에 인증부터 실 API |
| **Radix 학습 곡선** | 팀 전원이 처음일 수 있다 | 1주차에 E가 **30분 온보딩 + 예제 화면 1개**를 공유. 공통 컴포넌트(§6.5)가 대부분을 감싼다 |
| **커트라인 미적용** | "조금만 더 하면 되는데"로 전부 미완성 | 2주 금에 **공식적으로 버리는 결정**을 한다 (§4) |
| **화면 일관성 붕괴** | 5명이 각자 만든다 | 공통 컴포넌트 강제 + E의 리뷰 + 임의 hex 금지 |
| 프론트 배포 | Vercel Preview가 운영 API를 보면 사고 | Preview는 개발 API만 (`14-tech-stack.md` §3-7) |
| **쿠키가 안 붙음** | 교차 오리진인데 `credentials: 'include'`를 빠뜨리거나, 서버 CORS에 `Allow-Credentials`·정확한 오리진이 없으면 **로그인은 되는데 재발급만 조용히 실패**한다 | 1주차 공통 기반에서 **로그인 → 15분 후 재발급**을 실제로 통과시켜 본다. Preview 도메인도 허용 오리진에 넣을지 함께 결정 |
