## 1. 한 문장

> **중소 B2B 영업팀은 견적을 보낸 뒤 고객이 어떤 상태인지 알 수 없고, 최종 합의가 대화 속에 흩어져, 딜이 늘어지고 근거가 남지 않는다.**

---

## 2. 배경

중소 B2B 기업의 영업은 대부분 이렇게 돌아간다. 엑셀 양식에 품목과 단가를 채워 견적서를 만들고, 메일에 첨부해 보내고, 며칠 뒤 전화해서 "보셨어요?"라고 묻는다. 고객이 "그렇게 진행하시죠"라고 답하면 그 메일이 곧 계약의 근거가 되고, 담당자의 메일함이 곧 이력 저장소가 된다.

**도구가 없어서 생기는 문제가 아니다. 단계마다 도구가 끊겨 있어서 생기는 문제다.**

| 업무 단계 | 실제로 쓰는 도구 | 끊기는 지점 |
| --- | --- | --- |
| 견적 작성 | 엑셀 양식 | 단가 참조가 원본 시트에 묶여 있다 |
| 발송 | 메일 첨부 | 보내는 순간 추적이 끝난다 |
| 대기·추적 | 전화·기억 | **기록이 남지 않는다** |
| 승인 | 메일 회신·구두 | **어느 버전에 동의했는지 모른다** |
| 주문 확정 | 다시 엑셀 | 옮겨 적으며 오류가 난다 |
| 이력 보관 | 개인 메일함 | 담당자와 함께 사라진다 |

기존 ERP·그룹웨어가 대안이 되지 못하는 이유는 두 가지다. 영업 파이프라인만 필요한 팀에게는 지나치게 무겁고, **결정적으로 고객사가 계정을 만들어야 하는 순간 프로세스가 멈춘다.**

## 3. 대상 사용자

| 주체 | 하려는 일 | 지금 막히는 것 |
| --- | --- | --- |
| **영업 담당자** | 여러 고객사의 딜을 동시에 진행하며 견적을 반복 발송한다 | 어느 건을 언제 다시 챙겨야 하는지 판단할 근거가 없다 |
| **기업 관리자** | 팀 전체의 진행 상황을 파악하고 단가·상품을 관리한다 | 구두 보고 외에 현황을 알 방법이 없다. 단가를 고치면 과거 견적이 흔들린다 |
| **고객사 담당자** | 받은 견적을 검토하고 승인 여부를 알린다 | 계정을 만들 이유가 없다. 그래서 모든 응답이 메일과 전화로 돌아간다 |

세 주체 중 **고객사 담당자만 계정이 없다.** 이 비대칭이 문제의 성격을 결정한다 — 해법은 고객을 시스템 안으로 끌어들이는 것이 아니라, **계정 없이도 행동이 기록되게** 만드는 쪽이어야 한다.

## 4. 현재 흐름과 단절 지점

```
고객사 발굴 ─→ 상담 ─→ 견적 작성 ─→ 발송 ─→ 【 대 기 】─→ 응답 ─→ 주문 확정
                          │            │         │           │
                          ①            ②         ③           ④
                     버전이 쌓인다  추적이 끊긴다  근거가 없다  손으로 옮긴다
```

| # | 단절 지점 | 무슨 일이 벌어지는가 |
| --- | --- | --- |
| ① | 견적 작성 | 조건을 바꿀 때마다 파일이 늘어난다. 어느 것이 유효한지 파일명으로 관리한다 |
| ② | 발송 직후 | **가장 긴 구간이자 정보가 가장 없는 구간.** 고객이 열었는지, 검토 중인지, 잊었는지 알 수 없다 |
| ③ | 응답 | 승인이 말과 메일로 이루어진다. 시스템에는 아무것도 남지 않는다 |
| ④ | 주문 확정 | 합의된 내용을 다시 옮겨 적는다. 그 사이 단가가 바뀌었으면 금액이 어긋난다 |

**②가 이 문제 영역의 중심이다.** 딜이 늘어지는 시간의 대부분이 여기 있고, 영업 담당자가 통제할 수 없다고 느끼는 구간도 여기다.

## 5. 핵심 문제

### PB-01 · 견적을 보내고 나면 그 뒤가 보이지 않는다

> 화요일에 견적서를 메일로 보냈다. 목요일이 되었는데 답이 없다. 지금 전화하면 재촉하는 것 같고, 다음 주까지 기다리면 유효기간이 지난다. **판단할 정보가 없다.**

| | |
| --- | --- |
| **구조적 원인** | 메일 첨부는 전달 이후를 알려주지 않는다. 열람 여부가 발신자에게 돌아오는 경로가 없다 |
| **현재 대응** | 며칠 뒤 전화해서 확인한다 |
| **그 한계** | 담당자의 기억과 부지런함에 의존한다. 딜이 10건을 넘으면 반드시 놓치는 건이 생긴다 |
| **결과** | 팔로업 타이밍을 놓쳐 유효기간이 만료되고, 재작성·재발송으로 딜 주기가 길어진다 |

### PB-02 · 합의한 내용이 대화 속에 묻힌다

> 고객이 메일로 "네, 그 조건으로 진행해주세요"라고 답했다. 그런데 그 사이 견적서를 두 번 수정해 보냈다. **고객이 말한 '그 조건'이 어느 버전인지 메일만으로는 확정할 수 없다.**

| | |
| --- | --- |
| **구조적 원인** | 승인의 대상(견적)과 승인의 표시(메일 회신)가 서로 다른 곳에 있다 |
| **현재 대응** | 메일 스레드를 거슬러 올라가 첨부 파일을 확인한다 |
| **그 한계** | 시간이 지나거나 담당자가 바뀌면 복원이 사실상 불가능하다 |
| **결과** | 금액·수량 분쟁 시 근거를 제시할 수 없다. 신뢰 비용이 발생한다 |

### PB-03 · 견적 버전이 늘어나면 무엇이 유효한지 알 수 없다

> 조건을 조정해 세 번 다시 보냈다. 파일명은 `견적서_최종.xlsx`, `견적서_최종2.xlsx`, `견적서_진짜최종.xlsx`가 되었다.

| | |
| --- | --- |
| **구조적 원인** | 버전 간의 관계(무엇이 무엇을 대체했는가)가 파일명이라는 약한 규칙에만 담긴다 |
| **현재 대응** | 파일명 규칙과 담당자의 기억 |
| **그 한계** | 규칙은 사람마다 다르고, 급할 때 가장 먼저 깨진다 |
| **결과** | 폐기된 버전으로 주문이 진행된다. 고객이 본 것과 우리가 처리한 것이 달라진다 |

### PB-04 · 단가를 바꾸면 과거 견적이 흔들린다

> 이번 달부터 단가를 인상했다. 그런데 지난달 고객에게 보낸 견적서를 다시 열어보니 **금액이 바뀌어 있다.**

| | |
| --- | --- |
| **구조적 원인** | 견적이 상품 정보를 **참조**하고 있어서, 원본이 바뀌면 과거 문서까지 따라 바뀐다 (엑셀 수식 참조·DB 조인의 공통 함정) |
| **현재 대응** | 견적을 보낼 때마다 파일을 따로 저장한다 |
| **그 한계** | 저장을 잊으면 복원할 수 없고, 저장해도 흩어진다 |
| **결과** | **고객이 본 금액과 우리가 보는 금액이 달라진다 — PB-02의 근거 보존이 여기서 무너진다** |

### PB-05 · 담당자가 바뀌면 진행 맥락이 사라진다

> 담당자가 퇴사했다. 진행 중이던 딜 12건의 히스토리는 그 사람의 메일함과 머릿속에 있었다.

| | |
| --- | --- |
| **구조적 원인** | 이력이 개인의 도구(메일함·수첩)에 저장되고, 조직의 자산으로 축적되지 않는다 |
| **현재 대응** | 인수인계 문서를 쓴다 — 또는 쓰지 못한 채 넘어간다 |
| **그 한계** | 인수인계 문서는 결과만 담고 맥락을 담지 못한다 |
| **결과** | 고객에게 이미 한 질문을 다시 한다. 진행 중이던 건이 조용히 증발한다 |

## 7. 해결 방향

기능이 아니라 **원칙**이다. 어떤 기능을 만들든 이 다섯 가지를 지키면 위 문제가 풀린다.

| # | 원칙 | 푸는 문제 |
| --- | --- | --- |
| 1 | **견적은 파일이 아니라 추적 가능한 경로로 전달한다** — 계정 없는 고객도 열 수 있어야 한다 | PB-01 |
| 2 | **고객의 행동(열람·승인·반려)을 시스템 사건으로 기록한다** — 대화가 아니라 기록이 근거가 되게 한다 | PB-01·02 |
| 3 | **보낸 견적은 바꾸지 않는다** — 조건을 바꾸려면 새 버전을 만들고, 둘의 관계를 남긴다 | PB-02·03 |
| 4 | **금액과 품목은 보낸 시점의 값을 복사해 둔다** — 이후 카탈로그 변경과 분리한다 | PB-04 |
| 5 | **딜 하나를 담당의 축으로 삼는다** — 담당자가 바뀌면 딸린 이력이 함께 따라간다 | PB-05 |

## 8. 이번 범위에서 풀 문제와 풀지 않을 문제

### 푼다

견적 작성부터 **고객 승인을 거쳐 주문이 확정되기까지**의 구간. 그리고 그 구간을 성립시키는 최소한의 주변부(고객사·상품 카탈로그·담당 관리).

### 풀지 않는다 — 의도적으로

| 문제 | 풀지 않는 이유 | 근거 |
| --- | --- | --- |
| 주문 이후의 착수·검수·완료 관리 | 영업 관리가 아니라 프로젝트 관리 도구가 된다 | Q-09 |
| 계약서·세금계산서 | 발주 범위 밖 | Q-10 |
| 발송 전 상급자 결재 | 견적 상태 위에 결재 상태가 하나 더 얹힌다 | Q-06 |
| 회사별 영업 단계 커스터마이즈 | 단계가 데이터가 되면 규칙을 코드로 쓸 수 없다 | Q-11 |
| 기존 데이터 일괄 이관 | v1 범위 밖 (단, **첫 사용의 장벽이므로 재검토 필요** — `02-assumptions-and-risks.md` AS-06) | Q-13 |

### 다음 버전으로 미룬다

견적서 파일 다운로드(Q-04) · 복수 수신자 발송(Q-07) · 로고·직인(Q-05) · 할인 기능(Q-02) · 고객 문의 답변 화면(Q-20).

> ⚠️ 이 중 **파일 다운로드와 복수 수신은 문제 해결력에 직접 영향을 준다.** 근거와 위험은 `02-assumptions-and-risks.md` 참조.

## 9. 해결됐다고 판단하는 기준

문제별로 무엇이 달라져야 풀린 것인지 정의한다. **기능이 동작하는 것과 문제가 풀리는 것은 다르다.**

| 문제 | 판정 기준 |
| --- | --- |
| PB-01 | 발송된 견적 중 **열람까지 도달한 비율**, 발송 → 응답까지의 **소요 시간 중앙값**이 관측된다 |
| PB-02 | 승인 건의 **전부가 시스템 기록으로 남는다** — 승인 대상 견적이 하나로 특정된다 |
| PB-03 | 한 딜의 견적 목록에서 **무엇이 유효하고 무엇이 대체되었는지** 한눈에 구분된다 |
| PB-04 | 카탈로그 단가를 바꾼 뒤에도 **고객이 본 금액과 조회 금액이 일치한다** |
| PB-05 | 담당자 교체 후에도 **이전 이력 전체에 접근 가능하고**, 담당 없는 딜이 생기지 않는다 |
