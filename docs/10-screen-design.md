## 2. 디자인 시스템 — Radix Themes

### 2.1 왜 Primitives가 아니라 Themes인가

Radix는 두 층이다. **Primitives**는 스타일이 없는 헤드리스 라이브러리로 접근성과 키보드 동작만 제공하고 외형은 직접 만들어야 한다. **Themes**는 그 위에 색·간격·타이포·컴포넌트를 얹은 완성된 디자인 시스템이다.

**Themes를 택한 이유는 하나다 — 디자이너 없이 4주를 간다.** 색 스케일과 간격 체계를 직접 설계하는 비용을 감당할 수 없고, Themes는 Primitives를 포함하므로 접근성은 그대로 얻는다.

### 2.2 토큰 (확정)

| 항목 | 값 |
| --- | --- |
| accent color | **indigo** |
| gray color | **slate** |
| radius | **medium** — 카드 8px · 컨트롤 6px · 배지 4px |
| scaling | 100% |
| appearance | **light 고정** (§9 참조) |
| 본문 | 14px / 행간 20px (Text size 2) |
| 컨트롤 높이 | 32px (size 2) · 고객 화면의 주요 버튼만 40px (size 3) |
| 간격 | **4의 배수** — Radix space 1~9 (4·8·12·16·24·32·40·48·64) |
| 글꼴 | Radix 기본 시스템 스택 + 한글 폴백 (`Apple SD Gothic Neo`·`Malgun Gothic`·`Noto Sans KR`) |

### 2.3 색의 의미 — 하나의 색은 하나의 뜻만

| 뜻 | 스케일 | 쓰이는 곳 |
| --- | --- | --- |
| 기본 · 주요 동작 | **indigo** | 주요 버튼, 활성 탭, 견적 단계 강조 |
| **주목 · 사람이 봐야 할 것** | **amber** | 열람됨 배지, 단가 조정 표시, 되돌릴 수 없는 안내 |
| 성공 · 성사 | **green** | 성사 단계, 이달 성사 금액 |
| **위험 · 이미 늦은 것** | **red** | 비활성화 버튼, 마감 초과, 미읽음 알림 수 |
| 중립 | **slate** | 나머지 전부 |

> amber와 red를 섞지 않는 것이 규칙이다. amber는 "확인이 필요하다", red는 "되돌릴 수 없거나 이미 늦었다".

### 2.4 쓰는 컴포넌트

| 갈래 | 컴포넌트 |
| --- | --- |
| 레이아웃 | `Flex` · `Grid` · `Box` · `Container` · `Section` |
| 표시 | `Card` · `Heading` · `Text` · `Badge` · `Avatar` · `Separator` · `Table` · `Callout` |
| 입력 | `TextField` · `TextArea` · `Select` · `Checkbox` |
| 동작 | `Button` · `IconButton` · `DropdownMenu` · `Tabs` |
| 오버레이 | `Dialog` · `AlertDialog` · `Tooltip` |
| 아이콘 | `@radix-ui/react-icons` (Themes와 같은 18/16px 그리드) |

**쓰지 않는 것**: `Popover` · `HoverCard` · `Switch` · `RadioGroup` · `Slider` · `Progress` — v1 화면에 해당 상호작용이 없다. 필요해지면 추가 전에 화면 설계부터 고친다.

### 2.5 Dialog vs AlertDialog — 되돌릴 수 있는가로 가른다

| 모달 | 컴포넌트 | 이유 |
| --- | --- | --- |
| 견적 발송 | `Dialog` | 취소해도 잃는 것이 없다 |
| **승인 · 반려** | **`AlertDialog`** | 되돌릴 수 없다 — ESC·바깥 클릭으로 닫히면 안 된다 |
| **구성원 비활성화** | **`AlertDialog`** | 세션 종료와 딜 이관이 즉시 일어난다 |

`AlertDialog`는 확인 버튼에 자동 포커스를 두지 않는다 — 엔터 연타로 승인이 통과되지 않게.

### 2.6 접근성 — 무엇이 공짜이고 무엇이 아닌가

**Primitives가 주는 것** — 포커스 트랩, ESC 닫기, 배경 스크롤 잠금, `aria-*` 속성, 키보드 내비(Tabs 화살표 이동, Select 타이핑 검색), 포커스 링. 확인 모달 3종의 접근성 비용이 여기서 사라진다.

**직접 챙길 것**

| 항목 | 규칙 |
| --- | --- |
| **색만으로 정보를 전달하지 않기** | 열람/미열람은 **배지 색 + 아이콘 + 텍스트** 셋 다 — 색각 이상 사용자에게 색은 없는 정보다 |
| 폼 라벨 | `TextField`에 `label` 연결 (승인자 이름·직책, 견적 항목) |
| 표 헤더 | `Table.ColumnHeaderCell` 사용 — 견적서 품목 표 |
| 대비 | 본문은 slate-12, 보조는 slate-11까지만. slate-9 이하를 본문에 쓰지 않는다 |

## 3. 정보 구조

### 3.1 구성원 앱

```
대시보드          ← 로그인 후 진입점
고객사            목록 → 상세(담당자 · 딜 이력 · 활동)
딜                보드(단계별) → 상세(타임라인 · 견적 · 주문)
견적              목록 → 편집기 / 미리보기
주문              목록 → 상세
상품              목록 → 등록·수정                    [관리자만 편집]
──────────────
구성원            목록 · 초대 · 역할 변경 · 비활성화    [관리자 전용]
감사 로그         목록 → 상세                          [관리자 전용]
──────────────
알림              드롭다운 → 전체 목록
프로필            내 정보 · 비밀번호 · 알림 수신 설정
```

**딜이 허브다.** 견적·주문·활동·할 일은 전부 딜에서 파생되므로(SC-02~04), 목록 메뉴를 따로 두더라도 **작업의 시작점은 딜 상세**가 되도록 설계한다.

### 3.2 역할별 차이

| 화면·요소 | 기업 관리자 | 영업 담당자 |
| --- | --- | --- |
| 딜·견적·주문 목록 | 회사 전체 | **본인 담당만** |
| 담당자 필터 | 노출 | **숨김** (선택지가 자기 하나) |
| 상품 등록·수정 버튼 | 노출 | **숨김** (PR-09) |
| 딜 담당자 변경 | 노출 | **숨김** (DL-05) |
| 구성원 · 감사 로그 메뉴 | 노출 | **메뉴 자체를 숨김** |
| 대시보드 실적·전환율 | 노출 | 숨김 (DB-06~08) |

> 원칙: **권한 없는 기능은 비활성화가 아니라 숨긴다.** 눌러서 403을 만나게 하지 않는다. 서버는 그래도 검사한다(`FORBIDDEN`).

```
[로그인] → [대시보드]
                │
                ├─ 알림 클릭 ────────────────→ [딜 상세] 또는 [견적 상세]
                ├─ 응답 대기 클릭 ───────────→ [견적 상세]
                │
                └─ [딜 보드] → [딜 상세] ──┬─→ [견적 편집기] → [미리보기]
                                            │         └→ (발송 Dialog) → 발송 완료
                                            ├─→ 상담 기록 · 할 일 등록
                                            └─→ [주문 상세]  ← 전환

──────── 고객 (별도 앱) ────────
메일 링크 → [견적 열람] ─┬─→ (승인 AlertDialog) → [응답 완료]
                          ├─→ (반려 AlertDialog) → [응답 완료]
                          └─→ (문의 Dialog) → 접수 안내
                    만료 시 → [만료 안내]
```

| **탭 구성** | GAP-10 해소 — **상단은 요약, 이력은 타임라인 탭 하나로 통합**. 수동 기록과 자동 기록을 한 줄기로 섞어 보여준다 (AC-06·07) |
| 단계 표시 | 현재 단계만 indigo 솔리드 배지, 나머지는 gray. 성사는 흐리게 (수동 이동 불가) |
| 자동/수동 구분 | 자동 기록은 `[자동]` 배지 + 수정·삭제 없음 |
| 수정·삭제 | **본인이 작성한 것에만** 노출 (AC-04·05) |
| 단계 이동 | 상단 버튼으로. 협상에서 "다음 단계"를 누르면 *"성사는 승인된 견적을 주문으로 전환할 때 자동으로 처리됩니다"* 안내 |

### 6.1 상태 표시 — 전부 `Badge`

| 대상 | 표시 |
| --- | --- |
| 딜 단계 | 진행(리드~협상) = indigo soft / 현재 단계 = indigo solid / 성사 = green / 실패 = gray |
| 견적 상태 | 작성 중 = gray · **발송됨 = indigo** · **열람됨 = amber** · 승인됨 = green · 반려·회수·기간 만료 = gray |
| 열람 여부 | **amber `열람 N일 전` / gray `미열람 N일`** — 아이콘 + 텍스트 함께 (§2.6) |
| 자동 기록 | gray `자동` |

### 6.2 빈 화면 — 첫 사용 동선 (GAP-01 완화)

가입 직후 관리자가 처음 보는 대시보드는 비어 있다. 이때 `Card` 안에 **할 일 체크리스트**를 띄운다.

```
┌── 시작하기 ─────────────────────────────────┐
│  ☐ 1. 판매할 상품을 등록하세요    [등록하기]│
│  ☐ 2. 팀원을 초대하세요           [초대하기]│
│  ☐ 3. 첫 고객사를 등록하세요      [등록하기]│
│  ☐ 4. 첫 견적을 보내보세요                  │
└─────────────────────────────────────────────┘
```

각 목록 화면의 빈 상태도 **"없습니다"가 아니라 다음 행동을 제안**한다.

### 6.3 에러 처리 — `Callout` 또는 인라인

| 상황 | 화면 처리 |
| --- | --- |
| 404 (없음·권한 밖) | *"요청한 대상을 찾을 수 없습니다"* — **존재 여부를 구별하지 않는다** (SC-09) |
| 409 `STALE_VERSION` | `Callout`(amber) + **[새로고침] 버튼으로 재조회 후 재시도 유도** |
| 401 `REFRESH_TOKEN_NOT_ACTIVE` | 즉시 로그인 화면으로 이동 + *"세션이 만료되었습니다"* (AU-12) |
| 429 `LOGIN_LOCKED` | `Callout`(red) + 남은 시간 표시 |
| 403 `FORBIDDEN` | 정상 동선에서는 발생하지 않아야 한다(권한 없는 UI는 숨김). 발생 시 공통 문구 |
| 400 `VALIDATION_FAILED` | `fieldErrors`를 **`TextField` 아래**에 red 텍스트로 |

> 문구는 **API 명세서 부록을 그대로 쓴다.** 프론트에서 새로 쓰지 않는다.

> **인증이 아니라 신고 기록**이라는 점이 중요하다 — 계정 없는 응답자를 시스템이 검증할 방법은 없으므로, 과장하지 않고 "고객이 직접 입력한 정보"로 취급한다.
