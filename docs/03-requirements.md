## 1. 주체

| 주체 | 설명 |
| --- | --- |
| 플랫폼 관리자 | 2JO 서비스 운영자 |
| 기업 관리자 | 2JO에 가입한 회사의 관리 책임자 |
| 영업 담당자 | 해당 회사에 소속되어 영업을 수행하는 구성원 |
| 고객사 담당자 | 회사가 영업하는 대상. 2JO 계정을 갖지 않는다 |
| 방문자 | 아직 어느 회사에도 속하지 않은 사람 |

> 💡 "회사"는 2JO에 가입한 조직을, "고객사"는 그 회사가 영업하는 상대를 가리킨다. 이 문서에서 두 단어를 섞어 쓰지 않는다.

> 💡 **한 사람은 하나의 회사에만 속한다.** 따라서 이메일은 서비스 전체에서 유일하며, 로그인할 때 소속 회사를 고르는 절차는 없다. (Q-14)

## 2. 요구사항

### 2.1 기업 온보딩 — `ON`

💡 가입은 플랫폼 관리자가 직접 검토하여 승인한다. (Q-01)
💡 반려된 신청은 삭제하지 않고 이력으로 보존하며, 같은 이메일로 재신청할 수 있다. (Q-15)

| ID | 요구사항 |
| --- | --- |
| ON-01 | 방문자는 회사 정보를 입력하여 2JO 사용을 신청할 수 있다 |
| ON-02 | 신청자는 신청이 접수되었음을 확인할 수 있다 |
| ON-03 | 플랫폼 관리자는 가입 신청 목록을 조회할 수 있다 |
| ON-04 | 플랫폼 관리자는 가입 신청을 승인할 수 있다 |
| ON-05 | 플랫폼 관리자는 가입 신청을 반려할 수 있다 |
| ON-06 | 신청자는 승인 또는 반려 결과를 통보받는다 |
| ON-07 | 승인된 신청의 신청자는 해당 회사의 기업 관리자가 된다 |
| ON-08 | 플랫폼 관리자는 운영 중인 회사를 정지시킬 수 있다 |
| ON-09 | 정지된 회사의 구성원은 서비스를 이용할 수 없다 |
| ON-10 | 플랫폼 관리자는 정지를 해제할 수 있다 |
| ON-11 | 플랫폼 관리자는 회사의 영업 데이터를 조회할 수 없다 |
| ON-12 | 플랫폼 관리자는 회사 목록과 이용 현황을 조회할 수 있다 |
| ON-13 | 승인되기 전의 신청자는 서비스를 이용할 수 없다 |
| ON-14 | 플랫폼 관리자는 반려 사유를 기록할 수 있다 |

### 2.2 구성원 관리 — `MB`

💡 구성원 **삭제는 없다 — 비활성화만 존재한다.** 견적·주문·이력이 구성원을 참조하므로 물리 삭제는 이력을 깨뜨린다.

| ID | 요구사항 |
| --- | --- |
| MB-01 | 기업 관리자는 이메일로 직원을 초대할 수 있다 |
| MB-02 | 기업 관리자는 초대 시 역할을 지정한다 |
| MB-03 | 초대받은 사람은 초대 안내를 통해 계정을 생성할 수 있다 |
| MB-04 | 초대는 일정 기간이 지나면 만료된다 |
| MB-05 | 기업 관리자는 발송한 초대를 취소할 수 있다 |
| MB-06 | 기업 관리자는 초대를 재발송할 수 있다 |
| MB-07 | 기업 관리자는 구성원 목록을 조회할 수 있다 |
| MB-08 | 기업 관리자는 구성원의 역할을 변경할 수 있다 |
| MB-09 | 기업 관리자는 구성원을 비활성화할 수 있다 |
| MB-10 | 비활성화된 구성원은 서비스를 이용할 수 없다 |
| MB-11 | 회사에는 최소 한 명의 기업 관리자가 남아 있어야 한다 |
| MB-12 | 비활성화된 구성원이 담당하던 Deal은 다른 구성원에게 넘길 수 있다 (딸린 할 일은 Deal을 따라 자동 이동 — Q-29) |
| MB-13 | 이미 다른 회사에 속한 이메일은 초대할 수 없다 |
| MB-14 | 구성원을 비활성화할 때는 담당 Deal의 이관 대상을 지정해야 한다 (1건 이상일 때) — 지정 없이는 비활성화할 수 없다 |

### 2.3 인증 — `AU`

| ID | 요구사항 |
| --- | --- |
| AU-01 | 구성원은 이메일과 비밀번호로 로그인할 수 있다 |
| AU-02 | 구성원은 로그아웃할 수 있다 |
| AU-03 | 구성원은 매번 다시 로그인하지 않고 서비스를 이어서 이용할 수 있다 |
| AU-04 | 구성원은 본인 비밀번호를 변경할 수 있다 |
| AU-05 | 구성원은 비밀번호를 분실했을 때 재설정할 수 있다 |
| AU-06 | 로그인 시도가 반복해서 실패하면 일정 시간 로그인을 제한한다 (구체 수치는 AU-09) |
| AU-07 | 구성원은 본인 프로필(이름·연락처)을 조회하고 수정할 수 있다 |
| AU-08 | 플랫폼 관리자는 구성원과 다른 경로로 로그인한다 (관리자 페이지 별도, Q-22) |
| AU-09 | 5회 연속 로그인에 실패하면 10분간 로그인이 제한된다 |
| AU-10 | 구성원은 로그인 시 '로그인 상태 유지'를 선택하면 다시 로그인하지 않아도 세션이 유지된다 |
| AU-12 | 세션이 만료되거나 무효화되면 구성원은 로그인 화면으로 안내받는다 |

> AU-11(플랫폼 관리자 화면 비밀번호 재설정)은 다음 버전으로 미룸 — 4절 참조.

### 2.4 고객사 — `CU`

💡 사업자등록번호·주소 기록은 다음 버전으로 미룬다. (Q-19 → CU-13)
💡 고객사에는 담당 구성원 개념이 없다 — 등록자는 생성자로만 기록되며 접근 판정에 쓰지 않는다. 담당 범위는 Deal 기준이다. (SC-03)

| ID | 요구사항 |
| --- | --- |
| CU-01 | 구성원은 고객사를 등록할 수 있다 |
| CU-02 | 구성원은 고객사에 업종·규모·비고를 기록할 수 있다 |
| CU-03 | 구성원은 고객사 목록을 조회할 수 있다 |
| CU-04 | 구성원은 고객사를 이름으로 검색할 수 있다 |
| CU-05 | 구성원은 고객사 상세 정보를 조회할 수 있다 |
| CU-06 | 구성원은 고객사 정보를 수정할 수 있다 |
| CU-07 | 구성원은 고객사를 삭제할 수 있다 |
| CU-08 | 진행 중인 Deal이 있는 고객사는 삭제할 수 없다 |
| CU-09 | 구성원은 고객사에 담당자를 여러 명 등록할 수 있다 |
| CU-10 | 구성원은 고객사 담당자의 이름·직책·연락처·이메일을 기록할 수 있다 |
| CU-11 | 구성원은 고객사의 대표 담당자를 지정할 수 있다 |
| CU-12 | 구성원은 고객사에 속한 Deal 이력을 한눈에 볼 수 있다 |
| CU-14 | 견적 발송 이력이 있는 고객사 담당자는 삭제할 수 없다 |

> CU-13(사업자등록번호·주소)은 다음 버전으로 미룸 — 4절 참조.

### 2.5 Deal — `DL`

💡 Deal의 진행 단계는 서비스가 정한 것을 모든 회사가 동일하게 사용한다. 회사별로 단계를 바꿀 수 없다. (Q-11)

| ID | 요구사항 |
| --- | --- |
| DL-01 | 구성원은 고객사를 지정하여 Deal을 생성할 수 있다 |
| DL-02 | 구성원은 Deal에 예상 금액을 기록할 수 있다 |
| DL-03 | 구성원은 Deal에 희망 마감일을 기록할 수 있다 |
| DL-04 | 구성원은 Deal에 담당자를 배정할 수 있다 |
| DL-05 | 기업 관리자는 Deal의 담당자를 다른 구성원으로 변경할 수 있다 |
| DL-06 | 구성원은 진행 단계별로 정리된 Deal 현황을 볼 수 있다 |
| DL-07 | 구성원은 Deal을 다음 단계로 이동시킬 수 있다 (인접 단계로만. 견적 발송 시의 견적 단계 자동 승급은 시스템이 수행하는 예외 — Q-25) |
| DL-08 | 구성원은 Deal을 이전 단계로 되돌릴 수 있다 |
| DL-09 | Deal은 승인된 견적 없이 성사 상태가 될 수 없다 |
| DL-10 | 구성원은 Deal을 실패 처리할 수 있다 — 실패 처리하면 진행 중이던 견적과 열람 링크는 만료된다 (전이표 §5, 재개해도 복원되지 않음) |
| DL-11 | 구성원은 Deal 실패 사유를 기록할 수 있다 |
| DL-12 | 구성원은 실패 처리한 Deal을 다시 진행할 수 있다 |
| DL-13 | 구성원은 Deal 목록을 조회할 수 있다 |
| DL-14 | 구성원은 Deal을 고객사·담당자·단계로 걸러 볼 수 있다 |
| DL-15 | 구성원은 Deal 상세에서 상담 이력과 견적을 함께 볼 수 있다 |
| DL-16 | 구성원은 Deal을 삭제할 수 있다 |
| DL-17 | 견적이 연결된 Deal은 삭제할 수 없다 |
| DL-18 | Deal의 표시 금액은 성사 전에는 예상 금액(DL-02), 성사 후에는 연결된 주문의 합계다 — 성사 금액은 저장하지 않고 조회 시 계산한다 |

### 2.6 상품 카탈로그 — `PR`

### 2.13 알림 — `NT`

💡 채널은 수신자의 계정 유무로 결정된다. 구성원 대상 알림은 **인앱에 항상 기록**되고 메일은 병행 발송하며 수신 설정(NT-07)의 대상이 된다. 고객사 담당자 등 계정 없는 수신자에게는 **메일로만** 전달되며 이는 프로세스의 일부라 끌 수 없다. 인앱은 폴링 기반이며 실시간 푸시는 다음 버전이다. (Q-23)

**NT-12 수신자 규칙 — 실패한 메일별 (v1.6.1 확정)**

NT-12의 "담당 구성원"은 Deal 기반 메일에만 자명하므로, 실패한 메일의 종류별로 EMAIL_FAILED 인앱 알림의 수신자를 확정한다.

| 실패한 메일 | EMAIL_FAILED 인앱 수신자 |
| --- | --- |
| NT-02 견적 발송 안내 · NT-06 유효기간 임박 (고객 대상) | 해당 Deal의 담당 구성원 (Q-26 폴백 적용) — 수신인 확인 후 재발송(AP-13) 유도 |
| NT-01 초대 안내 | 초대 발송자(invited_by_member_id) — 발송자가 비활성이면 기업 관리자 폴백 (Q-26 준용) |
| NT-03~05·10 구성원 대상 메일의 병행 발송분 | 원 수신 구성원 본인 (인앱 알림은 이미 전달된 상태 — 메일 채널 이상 인지용) |
| NT-13 가입 승인·반려 통보 | **인앱 수신자 없음** — 신청자는 로그인 전(비밀번호 미설정)이고, 플랫폼 관리자는 인앱 알림 수신 구조가 없다(notification은 구성원 전용). **email_log FAILED 운영 지표(기술 스택 §1.5)가 유일한 감지 경로** |
| NT-14 비밀번호 재설정 안내 | **인앱 수신자 없음** — 수신자는 비밀번호를 잊어 로그인할 수 없다(인앱 알림은 로그인 후에만 보인다). NT-13과 같은 이유로 **email_log FAILED 운영 지표가 유일한 감지 경로** |

> NT-09(실시간 푸시)·NT-11(담당자 변경 고객 안내 메일)은 다음 버전으로 미룸 — 4절 참조.
